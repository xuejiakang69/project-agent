# 后端修改流程

## 核心原则

任何后端代码修改都必须遵循：

只读分析 → 确认信息 → 提出方案 → 等待用户确认 → 修改 → 验证 → 汇报

修改代码时，始终以最小必要改动为第一优先级。
- 优先修复当前问题，不主动重构整个模块。
- 优先复用项目现有的函数、组件、工具、依赖和业务逻辑。
- 优先修改现有代码，不随意创建新文件、新目录或新抽象层。
- 能修改一个函数解决的问题，不修改整个文件。
- 能修改少量代码解决的问题，不重写整个模块。
- 能使用现有依赖解决的问题，不新增依赖。
- 能通过局部修改解决的问题，不调整整体架构。
- 不随意修改函数名称、参数、返回值、接口路径、数据库结构及其他已有契约。
- 不主动添加与当前需求无关的功能、优化、异常处理或兼容逻辑。
- 不以代码风格统一、追求所谓最佳实践或使用最新技术为理由扩大修改范围。
- 不得跳过确认直接修改。

## 第一阶段：只读分析

首先检查：

- `back/` 目录结构；
- Python 版本；
- 实际 Web 框架；
- 依赖文件；
- 相关路由；
- 相关业务代码；
- 数据访问代码；
- 配置文件；
- 鉴权逻辑；
- 与本次任务直接相关的测试。

只读取与任务相关的内容。

不要修改文件。

## 第二阶段：确认信息

如果以下信息无法从项目现有代码中确定，并且会影响实现，则向用户询问：

- 技术方案；
- 接口契约；
- 业务规则；
- 数据结构；
- 权限要求；
- 错误处理方式；
- 是否允许修改依赖；
- 是否允许修改数据库。

不要自行猜测。

## 第四阶段：等待确认

没有得到用户明确确认之前：

- 不修改文件；
- 不创建文件；
- 不删除文件；
- 不安装依赖；
- 不修改数据库；
- 不执行会改变项目状态的命令。

以下回复可以视为确认：

- 确认
- 执行
- 可以
- 按这个方案改
- 开始修改

如果用户的回复仍然存在明显歧义，继续询问。

## 第五阶段：执行

只执行已经确认的修改。

不得因为发现其他问题而扩大修改范围。

如果发现新的重大问题：

1. 停止相关修改；
2. 说明新问题；
3. 等待用户确认。

## 第六阶段：验证

根据实际项目执行能够确认结果的验证。

例如：

- 启动检查；
- 接口检查；
- 参数校验；
- 测试；
- 类型检查；
- lint；
- 构建。

不要执行项目中不存在的测试命令。
